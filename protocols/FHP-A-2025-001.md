# Fair Hiring Protocol — API Surface (Draft v1.0)

This is the minimal, canonical API surface that any FHP compliant system must expose. It’s deliberately simple, stable, and explainability first.

We’ll define:
1.	Core Matching APIs
2.	Interpretation APIs (LLM driven)
3.	Ontology APIs
4.	Audit & Governance APIs
5.	Versioning APIs

This gives us a complete, interoperable protocol.

## 1. Core Matching APIs

These are the endpoints that actually perform matching.

### `POST /match`

**Purpose:**

Run the full matching pipeline (normalization → inference → scoring → bias → explanation).

**Request:**

```
{
  "candidate_profile": { ... },
  "job_brief": { ... }
}
```

**Response:**

```
{
  "match_status": "matched" | "rejected_constraints" | "rejected_must_have" | "rejected_low_score",
  "final_score": 0.76,
  "match_id": "uuid",
  "protocol_version": "1.0.0"
}
```

**Notes:**
- 	This endpoint does not return the explanation — that’s /explain.
- 	This keeps the match response lightweight.

---

### `GET /explain/{match_id}`

**Purpose:**

Return the full explanation for a match.

**Response:**

```
{
  "match_explanation": { ... },   // matches the schema
  "candidate_summary": "...",
  "company_summary": "..."
}
```

**Notes:**
- 	This is the “contract of fairness.”
- 	Everything must be trace derived.

---

### `POST /batch/match`

**Purpose:**

Efficiently match one candidate to many jobs.

**Request:**

```
{
  "candidate_profile": { ... },
  "job_briefs": [ ... ]
}
```

**Response:**

`Array of match results.`

The system loops:
```
for each job in job_briefs:
    run full matching pipeline
```

OR

**Purpose:**

Efficiently match one job to many candidates

**Request:**

```
{
  "job_brief": { ... },
  "candidate_profiles": [ ... ]
}
```

**Response:**

`Array of match results.`

The system loops:
```
for each candidate in candidate_profiles:
    run full matching pipeline
```

**Why this works**
Because the matching pipeline is symmetric:
-	It always takes one candidate and one job
-	It always produces one match result
-	It always produces one explanation
-	It always logs one trace set

So batching is just:
```
repeat the single-match pipeline N times
```

The API simply needs to enforce:
-	Either candidate_profile + job_briefs[]
-	Or job_brief + candidate_profiles[]
-	Never both

This keeps the API surface clean and avoids duplication.

**What the response looks like**

Regardless of direction, the response is always:
```
{
  "results": [
    {
      "match_id": "uuid",
      "match_status": "matched",
      "final_score": 0.76,
      "candidate_id": "...",
      "job_id": "..."
    },
    ...
  ]
}
```

Each result can be retrieved later via:
-	/explain/{match_id}
-	/audit/match/{match_id}

**Why this matters architecturally**

This design gives:

✔ Efficiency

Batching avoids repeated overhead (model loading, ontology loading, etc.)

✔ Simplicity

One endpoint, two modes, no duplication.

✔ Flexibility

Platforms can use it for:
-	“Show me all jobs this candidate fits”
-	“Show me all candidates for this job”
-	“Bulk refresh all matches nightly”
-	“Re-run matches after ontology update”
-	“Re-run matches after scoring update”

✔ Determinism

Each match is still atomic and fully explainable.

## 2. Interpretation APIs (LLM driven)

These endpoints expose the interpretation layer — the part where LLMs shine.

These are optional for companies, but required for reference implementations.

### `POST /interpret/candidate`

**Purpose:**

Turn a raw CV or profile into a canonical Candidate Profile.

**Request:**

```
{
  "raw_text": "CV text or structured data"
}
```

**Response:**

```
{
  "candidate_profile": { ... },
  "inferred_skills": [ ... ],
  "inferred_transferable_skills": [ ... ],
  "model_outputs": { ... }
}
```

---

### `POST /interpret/job`

**Purpose:**

Turn a raw job description into a canonical Job Brief.

**Request:**
```
{
  "raw_text": "JD text"
}
```

**Response:**

```
{
  "job_brief": { ... },
  "inferred_requirements": [ ... ],
  "responsibility_skill_mappings": [ ... ]
}
```

---

### `POST /validate/inference`

**Purpose:**

Run multi model validation on arbitrary text.

**Request:**

```
{
  "text": "some text",
  "task": "skill_extraction" | "responsibility_mapping" | "semantic_expansion"
}
```

**Response:**

```
{
  "validated_output": [ ... ],
  "model_raw_outputs": { ... },
  "disagreements": [ ... ],
  "resolution": "intersection_only"
}
```

This is the public face of the multi model layer.

## 3. Ontology APIs

These expose the canonical skill ontology.

### `GET /ontology/skills`

Returns the full skill ontology.

---

### `POST /ontology/resolve`

Purpose: Resolve a skill into its canonical form + equivalents.

**Request:**

```
{
  "skill": "PostgreSQL"
}
```

**Response:**

```
{
  "canonical": "PostgreSQL",
  "equivalents": ["Relational Database"],
  "aliases": ["Postgres"],
  "transferable_compensations": ["SQL"]
}
```

## 4. Audit & Governance APIs

These make the system transparent and accountable.

### `GET /audit/match/{match_id}`

Returns the full trace log for a match.

**Response:**

```
{
  "trace": [
    { "stage": "normalization", ... },
    { "stage": "inference", ... },
    { "stage": "semantic_expansion", ... },
    ...
  ]
}
```

---

### `GET /audit/fairness`

Returns fairness metrics for the system.

**Response:**

```
{
  "disparate_impact": { ... },
  "equal_opportunity": { ... },
  "score_skew": { ... },
  "drift": { ... }
}
```

---

### `GET /governance/version`

Returns the current protocol version and component versions.

**Response:**

```
{
  "protocol_version": "1.0.0",
  "scoring_version": "1.0.0",
  "bias_version": "1.0.0",
  "ontology_version": "2025.02",
  "models_used": ["model_A_v3", "model_B_v2"]
}
```

## 5. Why this API surface works

It is:
- 	minimal (only what’s needed)
- 	stable (versioned, predictable)
- 	explainability first (explanations + traces are first class citizens)
- 	model agnostic (interpretation endpoints can use any LLMs)
- 	future proof (ontology + governance endpoints)
- 	auditable (full trace access)
- 	modular (companies can use only what they need)

And crucially:

*It enforces the architecture — LLMs interpret, heuristics decide, and everything is explainable.*
