# Fair Hiring Protocol (FHP) — Canonical Specification v1.0 (Draft)

The Fair Hiring Protocol defines the rules, data structures, processes, and fairness guarantees required for any system that performs automated or semi automated job–candidate matching.

This protocol is singular, canonical, and **non-forkable**. Implementations may vary, but the **protocol must not.**

## 1. Purpose

The Fair Hiring Protocol exists to:
- 	ensure transparent, bias aware, human respecting hiring
- 	standardize how job requirements and candidate profiles are represented
- 	define a universal matching process
- 	guarantee fairness, auditability, and accountability
- 	prevent discrimination, opacity, and arbitrary filtering

The protocol is a **public good**, _not_ a commercial asset.

## 2. Scope

The FHP governs:
- 	data schemas
- 	matching logic
- 	scoring rules
- 	transparency requirements
- 	fairness constraints
- 	audit logging
- 	governance processes

The FHP does not govern:
- 	UI design
- 	storage engines
- 	deployment models
- 	client applications
- 	performance optimizations

Those are implementation details.

## 3. Canonical Nature

### 3.1. Single Source of Truth

There is **one canonical version** of the Fair Hiring Protocol at any given time.

### 3.2. No Forking of the Protocol

Implementations **must not** modify:
- 	matching logic
- 	fairness rules
- 	scoring criteria
- 	bias mitigation requirements
- 	transparency obligations

Implementations **may** extend functionality, but **must not** alter the core.

### 3.3. Compliance Requirement
A system may only claim FHP compliance if it:
- 	implements the protocol exactly
- 	passes the compliance test suite
- 	exposes required transparency endpoints
- 	adheres to fairness constraints

## 4. Data Model

The FHP defines canonical schemas for:

### 4.1. Candidate Profile
- 	skills (structured)
- 	experience (structured)
- 	preferences
- 	constraints
- 	availability
- 	location (optional)
- 	anonymized demographic attributes (for bias monitoring only)

### 4.2. Job Brief
- 	required skills
- 	optional skills
- 	responsibilities
- 	constraints
- 	salary range
- 	seniority level
- 	working conditions

### 4.3. Skill Ontology

A shared, versioned ontology defining:
- 	skill equivalence
- 	skill hierarchy
- 	transferable skills
- 	domain clusters

This ontology is community maintained and versioned.

## 5. Matching Logic

The FHP defines a deterministic, auditable matching pipeline:

### 5.1. Normalization

Convert all inputs into structured representations.

### 5.2. Semantic Expansion

Infer equivalent and related skills using the shared ontology.

### 5.3. Constraint Satisfaction

Hard constraints **must** be satisfied before scoring.

### 5.4. Scoring

Score candidates using:
- 	skill match
- 	experience relevance
- 	transferable skills
- 	preference alignment

### 5.5. Bias Aware Adjustment

The system **must**:
- 	detect demographic skews
- 	correct systemic bias
- 	ensure parity across protected groups

### 5.6. Explanation Generation

Every match **must** include:
- 	the reasoning
- 	the criteria
- 	the score breakdown
- 	the inferred skills
- 	the constraints that mattered

## 6. Transparency Requirements

### 6.1. Mandatory Explanations

Every recommendation and rejection **must include** a machine readable explanation.

### 6.2. Version Disclosure

Every match must state:
- 	protocol version
- 	ontology version
- 	scoring module version

### 6.3. Audit Logs

All decisions **must** be logged with:
- 	inputs
- 	outputs
- 	explanations
- 	fairness metrics
- 	timestamps

Logs **must** be exportable for external audit.

## 7. Fairness Guarantees

### 7.1. No Arbitrary Filters

The system **must not** allow filtering by:
- 	age
- 	gender
- 	ethnicity
- 	university
- 	years since graduation
- 	employment gaps
- 	nationality
- 	disability

### 7.2. Candidate Autonomy

Candidates **must** be able to:
- 	control visibility
- 	correct inferred skills
- 	hide sensitive attributes
- 	delete their profile

### 7.3. Outcome Monitoring

The system **must** continuously measure:
- 	recommendation parity
- 	interview parity
- 	offer parity
- 	salary parity

### 7.4. Drift Detection

If bias emerges, the system **must**:
- 	detect it
- 	flag it
- 	prevent further matches until corrected

## 8. Governance

### 8.1. Community Driven

Changes to the protocol **must** be:
- 	proposed publicly
- 	reviewed publicly
- 	justified with fairness impact analysis

### 8.2. Versioning

The protocol uses semantic versioning:
- 	MAJOR: fairness logic changes
- 	MINOR: ontology updates
- 	PATCH: clarifications

### 8.3. Canonical Repository

There is **one canonical repository** for:
- 	the protocol
- 	the ontology
- 	the compliance suite

### 8.4. Compliance Certification

Implementations **must** pass:
- 	schema validation
- 	scoring validation
- 	fairness validation
- 	transparency validation

## 9. Implementation Independence

### 9.1. Model Agnostic

The protocol **does not** mandate:
- 	which LLM
- 	which embedding model
- 	which vector DB
- 	which runtime

### 9.2. Multi Model Validation

Implementations **must** validate matches using:
- 	at least two independent models
- 	cross model consistency checks

### 9.3. No Vendor Lock In

The protocol **must** remain:
- 	open
- 	free
- 	interoperable

## 10. Security & Privacy

### 10.1. Minimal Data Retention

Store **only** what is necessary for matching.

### 10.2. Zero Knowledge Matching (Long Term Goal)

The protocol aims toward:
- 	encrypted candidate profiles
- 	encrypted job briefs
- 	matching without exposing raw data

### 10.3. No Surveillance

The system **must not**:
- 	scrape
- 	track
- 	profile
- 	infer sensitive attributes without consent

**This is the core.**

***This is the thing that cannot be forked. This is the foundation for everything else.***
